# HardTasks

Веб-застосунок для виконання трудомістких обчислювальних задач (розв'язання СЛАР
методом Гауса) з балансуванням навантаження між кількома application-серверами.

## Ідея
Користувач реєструється, ставить задачу, бачить прогрес, місце в черзі та
приблизний час очікування, може скасувати задачу й переглянути історію.
Запити розподіляє nginx між app-серверами, задачі виконують воркери на різних
серверах. Якщо черга росте, автоскейлер сам додає сервери.

## Можливості
- Задача СЛАР (метод Гауса з вибором головного елемента), обмеження n
Користувач реєструється, ставить задачу (розв'язання СЛАР методом Гауса, бачить прогрес, чергу з приблизним часом
очікування, може скасувати задачу й переглянути історію. Запити розподіляє
nginx між кількома app-серверами, задачі виконують воркери на різних серверах.

## Можливості
- Задачі: СЛАР (метод Гауса з вибором головного елемента)
- Прогрес у реальному часі, скасування, історія задач
- Черга з орієнтовним часом очікування (оцінка за розміром задачі)
- Авторизація (bcrypt + JWT в httpOnly cookie), HTTPS
- Load balancer (nginx), мінімум 2 app-сервери
- Автоскейлінг контейнерів з верхнім лімітом
- Адмін-панель моніторингу (/admin)
- Автотести: pytest (юніт/інтеграційні) і Playwright (API)

## Архітектура
    Клієнт -> nginx (HTTPS) -> app-1..N (FastAPI + воркер) -> PostgreSQL
                                   ^
                    autoscaler (Docker SDK) стежить за чергою

- Задачі й черга зберігаються в PostgreSQL. Воркер бере задачу через
  `SELECT ... FOR UPDATE SKIP LOCKED`, тож кожна задача виконується рівно одним сервером.
- Воркер пише прогрес кожні ~0.5 с; та сама операція повертає прапор скасування.
- Воркери шлють heartbeat у таблицю `workers`. Якщо контейнер зупинено,
  його задачі автоматично повертаються в чергу.
- nginx резолвить ім'я `app` через Docker DNS (кожні 5 с), тому нові
  контейнери автоскейлера підхоплюються без перезапуску.
- Кожна відповідь має заголовок `X-Served-By` (видно, який сервер відповів).
- Час очікування: складність СЛАР ~ n³, коефіцієнт береться з історії виконаних
  задач; черга розподіляється по воркерах, що звільняються найраніше.

## Запуск
    cp .env.example .env          # змінити паролі й SECRET_KEY
    bash scripts/gen_cert.sh      # самопідписаний сертифікат (або mkcert, див. нижче)
    docker compose up --build

Відкрити https://localhost. Адмін-панель: https://localhost/admin
(логін/пароль з `.env`: ADMIN_USERNAME / ADMIN_PASSWORD; якщо змінити пароль у
`.env`, при наступному старті app він синхронізується з базою).

Довірений сертифікат без попередження браузера (Windows):
    mkcert -install
    mkcert -cert-file nginx/certs/cert.pem -key-file nginx/certs/key.pem localhost 127.0.0.1
    docker compose restart nginx

## Масштабування
Вручну: `docker compose up --scale app=3`.
Автоматично: сервіс `autoscaler` додає сервер, якщо черга не порожня 2 перевірки
поспіль (~20 с; поріг `SCALE_UP_QUEUE`), до `MAX_APPS`. Прибирає зайві після
`SCALE_DOWN_IDLE` секунд простою (не нижче `MIN_APPS`).

## Налаштування (.env)
| Змінна | За замовчуванням | Опис |
|--------|------------------|------|
| MAX_LINEAR_N | 10000 | максимальний розмір системи |
| MAX_ACTIVE_PER_USER | 3 | активних задач на користувача |
| WORKER_THREADS | 1 | воркерів у кожному app-контейнері |
| MIN_APPS / MAX_APPS | 2 / 5 | межі автоскейлінгу |
| SCALE_UP_QUEUE | 1 | скільки задач мають чекати для масштабування |
| SCALE_DOWN_IDLE | 60 | секунд простою перед зменшенням |

## API
| Метод | Шлях | Опис |
|-------|------|------|
| POST | /api/register, /api/login, /api/logout | авторизація |
| GET | /api/me | поточний користувач |
| POST | /api/tasks/linear | нова задача СЛАР `{n}` |
| GET | /api/tasks, /api/tasks/{id} | історія / статус, прогрес, ETA |
| POST | /api/tasks/{id}/cancel | скасування |
| GET | /api/tasks/{id}/result | результат |
| GET | /api/admin/stats | статистика (тільки адмін) |
